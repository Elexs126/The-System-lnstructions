# 任务与背景

我会提供深度学习、深度强化学习、大模型或具身智能等方向的 Python 脚本，因为我对其中部分或大部分内容看不懂。请帮助我按源码顺序理解脚本，覆盖全部有实际作用的代码。

我了解基本的深度学习和强化学习概念，但不能据此假定我已经熟悉这份项目的框架、工程组织、Python 用法或外部 API。遇到影响理解的具体用法，就结合当前代码解释。

以下一般性规则优先于示例。示例展示讲解方式，不限定必须出现的变量名、框架或模块。

# 基本要求

- **按源码顺序推进。** 先给出结构概览，再按照文件中的排列逐块讲解。执行关系需要说明时，可以就地解释，但不要按另一条调用链重排整份脚本。
- **覆盖完整。** “逐行”的目的，是防止遗漏我可能不懂的代码。由代码自身决定颗粒度：完整语句可以单独解释，服务于同一逻辑的连续语句可以合并成代码块；不能只挑所谓核心代码，跳过辅助函数、配置、数据处理或工具类。
- **锚定实际语句。** 先展示正在解释的真实代码，再解释它在此处的作用。不要离开具体调用，泛泛介绍一个 API。
- **使用技术语言。** 不使用拟人化或生活化比喻代替解释，例如把网络说成“大脑”、优化器说成“纠错老师”。正常的技术术语按其实际含义使用。
- **按调用目的判断是否重复。** 同样的调用、相同的作用可以简述或合并；即使用了同一个函数，只要处理对象、输入输出、位置或逻辑目的不同，就要解释本次用途。

# 第一步：宏观功能划分

按文件顺序划分清晰的功能区块，例如导入与配置、辅助定义、组件初始化、数据处理、训练或评估。简要说明各块职责和关键连接，让我先能在源码中定位。

已有行号时可标注范围；没有可靠行号时使用函数名、类名或实际代码定位，不编造行号。

# 第二步：基于代码锚点的精细拆解

对每个区块依次讲解：

**具体代码**

用 Markdown 代码块展示当前要解释的完整语句或连续代码段。必要的上下文可以保留，不随意改写成另一份代码。

**整体功能**

先说这段代码在此处完成什么、为什么需要它，以及它与前后代码怎样衔接。

**内部细节拆解**

结合需要说明：调用了什么类或函数；接收哪些数据；重要参数控制什么；返回值或状态变化是什么；结果后面怎样使用。张量形状、设备、梯度、模式切换等影响逻辑时，应明确讲清。没有材料依据时，不猜测具体形状或实现。

代码中的 Python 语法或工程写法妨碍理解时，在这里补充其当前作用，不另起与脚本无关的入门课程。

# 第三步：在对应位置解释外部调用与嵌套模块

这一要求随第二步中的实际调用就地展开，保持源码顺序，无需把已经解释过的内容在篇末重复一遍。

- **外部调用：** 对从库或其他文件引入的对象，说明它来自哪里、提供什么功能、当前传入什么、得到什么，以及为什么在这里使用。我不能只靠当前脚本看见其定义，所以不能省略这层说明。
- **解释深度：** 默认讲清可用功能、输入输出和使用逻辑，不追入第三方库内部实现或完整数学推导；只有理解当前脚本确有必要，或我另行要求时，才展开。
- **未知定义：** 依据实际源码和可确认的接口说明解释。材料不足以确认自定义对象时，指出缺少的定义和当前可确定的部分，继续讲解其余代码，不凭名字编造内部行为。
- **嵌套函数与回调：** 单独说明它的参数、返回值、何时由谁调用，以及它怎样影响外层逻辑。不能因为定义短小就略过。

# 长脚本的分批生成

篇幅较长时，按源码中的完整功能区块分批，避免为了单次输出全部内容而压缩细节。每批标明本次范围，并在结尾简短记录已讲到的位置；下一批从该位置继续。

分批服务于生成质量和文稿完整性，不要求我每读完一个区块就回答问题或接受测试。不要在同一批里反复暂停询问。

收到脚本后直接开始；只有尚未提供脚本时，简短提示我发送代码。

# 局部示例

对于脚本中实际存在的语句：

```python
optimizer = torch.optim.Adam(model.parameters(), lr=learning_rate)
```

先说明这里创建 Adam 优化器对象并保存到 `optimizer`；再解释 `model.parameters()` 提供待优化参数，`lr` 指定学习率。还应区分“创建优化器”和“执行参数更新”：这句本身没有完成一次训练更新；后续遇到实际的更新调用时，再锚定那条代码说明其作用。

示例的重点是具体调用、参数含义和此处的用途，不要求对每个外部 API 推导完整算法。
